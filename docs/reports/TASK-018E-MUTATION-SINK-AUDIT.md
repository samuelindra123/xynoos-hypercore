## Identity, telemetry and sequencing

`Binding::discover` binds the current manager PID/start identity, systemd unit/invocation, delegated subgroup, process membership and held cgroup descriptors; `revalidate` rereads and compares them ([systemd_identity.rs:159](../../crates/xynoos-linux-control/src/systemd_identity.rs#L159), [systemd_identity.rs:239](../../crates/xynoos-linux-control/src/systemd_identity.rs#L239), [systemd_identity.rs:302](../../crates/xynoos-linux-control/src/systemd_identity.rs#L302)). The manager hierarchy verifier checks empty parent, manager membership, descendant counts and registered child ([controller.rs:1330](../../crates/xynoos-linux-control/src/controller.rs#L1330)). Descriptor-relative opens use no-follow and bounded reads ([transaction.rs:528](../../crates/xynoos-linux-control/src/transaction.rs#L528)); child reads verify held and named identities ([bound_child.rs:89](../../crates/xynoos-linux-control/src/bound_child.rs#L89)).

Adapter guard recollects telemetry at each permitted mutation and revalidates the session; refusal latches forward authority, while recovery still requires a fresh eligible reading ([session_adapter.rs:90](../../crates/xynoos-linux-control/src/controller/session_adapter.rs#L90), [safety.rs:89](../../crates/xynoos-linux-control/src/safety.rs#L89)). Checks and syscalls are sequential: neither fresh telemetry nor descriptors prove exclusive delegation or provide compare-and-swap. A competing actor can race between a check and a write/removal. These are barriers to enabling physical mutation, not claims of a presently reachable built-in write.

## Forward and recovery transitions

`forward` ([empty_child_coordinator.rs:211](../../crates/xynoos-linux-control/src/empty_child_coordinator.rs#L211)) requires authorization and a positive aligned bounded request; validates binding, empty parent, original controller set and memory availability; activates and verifies; creates and verifies one empty child; captures low; verifies expected low before apply and verifies applied value; verifies requested value before restoration and verifies original; verifies emptiness, removes and verifies absence; restores controllers and verifies final state. Cancellation is checked at each `step`; checks immediately preceding apply, restore, and post-removal also return failures before the next mutation.

`run` ([empty_child_coordinator.rs:386](../../crates/xynoos-linux-control/src/empty_child_coordinator.rs#L386)) recovers only a `Before` failure after initial capture. Conflict, ambiguous or unavailable faults lead to diagnostics without automatic writes. `recover` ([empty_child_coordinator.rs:502](../../crates/xynoos-linux-control/src/empty_child_coordinator.rs#L502)) validates binding and controller state, then requires the registered child identity, no population/descendants and the expected current low. If applied, it restores only from the requested value and verifies original; it removes and verifies the child before rechecking absence and restoring and verifying controllers. Failure stops the sequence; ambiguous operations are not retried. Recovery does not accept further cancellation. Adapter latches prevent treating a post-write identity error as a harmless pre-write failure ([session_adapter.rs:189](../../crates/xynoos-linux-control/src/controller/session_adapter.rs#L189)). These guarantees depend on an honest backend and do not eliminate check/write races.

`transaction::run_during` is a separate generic path ([transaction.rs:66](../../crates/xynoos-linux-control/src/transaction.rs#L66)): authorization and snapshot freshness precede apply; a write error is ambiguous and receives no callback or rollback; successful apply is checked, callback runs, `ready_to_restore` must succeed, then identity and expected value are checked before rollback and original is read back. It does not recollect telemetry for rollback and assumes its backend and callback honor their contracts. It is not a substitute for the adapter's fresh recovery gate.

## Worker lifecycle

The only controlled-worker call site is `controlled` ([optimization_experiment.rs:363](../../crates/xynoos-decision/examples/optimization_experiment.rs#L363)); it is not dispatched: `controlled` CLI returns an error ([optimization_experiment.rs:490](../../crates/xynoos-decision/examples/optimization_experiment.rs#L490)), and construction is independently disabled. The worker blocks on stdin before allocation ([optimization_experiment.rs:130](../../crates/xynoos-decision/examples/optimization_experiment.rs#L130)); the callback spawns, places, verifies membership and telemetry, checks cancellation, then releases; it polls completion or timeout ([optimization_experiment.rs:388](../../crates/xynoos-decision/examples/optimization_experiment.rs#L388)). Every ordinary callback result passes `stop_and_reap`, which uses `try_wait`, kill and a two-second bounded reap check ([optimization_experiment.rs:101](../../crates/xynoos-decision/examples/optimization_experiment.rs#L101)). Failure marks the target unresolved, blocking restoration and preserving it ([optimization_experiment.rs:433](../../crates/xynoos-decision/examples/optimization_experiment.rs#L433), [transaction.rs:403](../../crates/xynoos-linux-control/src/transaction.rs#L403)). Cleanup is explicit and its failure prevents success; conflict, ambiguity and rollback failure preserve the target ([optimization_experiment.rs:442](../../crates/xynoos-decision/examples/optimization_experiment.rs#L442)).

This analysis covers ordinary returns, not process abort, SIGKILL or panic across the callback. In those cases no durable recovery record exists and a worker or hierarchy may remain. The unrelated read-only experiment's `Guard` uses best-effort kill and blocking wait ([optimization_experiment.rs:11](../../crates/xynoos-decision/examples/optimization_experiment.rs#L11)); it does not operate the controlled cgroup. Systemd service inactivity is not proof that resource restoration or hierarchy cleanup succeeded.

## Findings and remediation

1. Launcher cleanup verification: `unit-preflight` previously called path absence verified removal without retaining the containing hierarchy identity. A changed ancestor or mount could make the lookup refer to a different hierarchy. The launcher now reports absence as **unverified** and returns failure; it cannot prove removal from the available evidence. This deliberately makes `unit-preflight` fail closed until independently bound cleanup verification exists ([launcher:38](../../scripts/xynoos-018d-launcher.sh#L38)).
2. Launcher service state: a `LoadState=not-found` substring previously won even alongside `ActiveState=active` or `failed`. Exact single load and active fields are now required, with `ActiveState=inactive` ([launcher:27](../../scripts/xynoos-018d-launcher.sh#L27)). The fixture exercises contradictory state and absent hierarchy evidence ([test-018e-launcher.sh](../../scripts/tests/test-018e-launcher.sh)). No physical mutation guard was relaxed.

## Unreviewed and physical readiness

- **UNREVIEWED: external consumer backend implementations and operating system/systemd internals.** They are not present in this repository; the generic traits cannot constrain them. The systemd launcher is an external mutation path and is not a guarantee of exclusive control.
- **UNVERIFIED: actual kernel and systemd behavior**, including delegation exclusivity, TOCTOU races, short or partial writes and read-back, termination/reap and independent hierarchy cleanup. No physical transaction or live service was run in this audit. Prior live observations, if any, are not independent evidence from this audit.
- **UNVERIFIED: crash recovery and recovery with unavailable telemetry on a real hierarchy.** Progress and latches are in memory, not a durable journal. Fixtures show refusal/preservation, not physical cleanup. Before any physical transaction, design and validate durable recovery, independent retained hierarchy identity, exclusive delegation and operator procedures for unavailable telemetry and ambiguous writes.

The implementation remains disabled and is **not production-ready**. No performance conclusion follows from this audit.

# TASK 015A — telemetry reliability

## Contract and operation

`system snapshot --json [--disk NAME] [--freshness-ms N]` emits one JSON object; `system sample --json --count N --interval-ms N [--disk NAME] [--freshness-ms N]` emits one JSON object per line. Sampling bounds are the existing TASK 013 bounds. Default freshness is 5000 ms. The legacy human snapshot and CSV sampling remain; CSV retains its column order, but disk fields are now empty unless `--disk` is supplied. Empty CSV cells do not distinguish errors: automation that needs status must use JSON. TASK 013 pressure commands are unchanged.

Schema version 1 has `schema_version`, wall-clock `timestamp_unix_ms` (nullable if before the Unix epoch), `monotonic_start_ns` (nullable process-local offset, comparable only within the same process), collection duration, freshness threshold, `sequential: true`, and a map of named readings. Each reading has source, scope, unit, status, value, error and conservative age in nanoseconds measured from the **start** of collection with `Instant`. Observations are sequential; timestamps do not imply simultaneous kernel state. Consumers must check status before using a value; stale values may remain present. Error text is diagnostic, not a stable enum. Version 1 consumers must ignore unknown fields and handle unknown status values as unavailable; incompatible semantics require a new schema version. No IPC transport or controller is provided.

Statuses are `available`, `unsupported`, `permission_denied`, `read_error`, `parse_error`, `stale`, `not_yet_sampled`, `unavailable`, and `truncated`. Parse errors include malformed, missing, overflow, reset, bounds and identity failures, with details in error. CPU and disk deltas need two successful samples with positive monotonic intervals, matching disk identity and no counter reset; both samples must be within the freshness threshold. A first sample is not yet sampled. PSI values are avg10 percentages; CPU ticks use USER_HZ; meminfo and cgroup memory/I/O are bytes, cgroup CPU is microseconds, disk sectors are 512-byte sectors and disk deltas are bytes. Capability readings carry their actual units.

Disk selection is deliberately explicit: there is no representative default. Names are matched exactly against visible diskstats; major, minor and name must match across samples. Missing selections are unavailable. `sysfs_class` is `virtual`, `device_backed`, or `unknown` based on the resolved sysfs path; device-backed is not proof of physical hardware, particularly in a VM or container. Major/minor/name cannot detect removal and recreation between observations with the same identity.

Discovery examines at most 256 directory entries per pass plus one to detect truncation; partial entries are retained and a `truncated` discovery status is emitted. Enumeration order and the retained subset can vary, and separate attribute passes are not atomic. Attribute values are bounded to 4096 bytes; input files are bounded to 1 MiB. Discovery counts are attributes, not unique hardware counts. Not all existing snapshot fields are exposed in schema v1; this is a minimal contract. Permission and unsupported states describe what this process can see, not host-wide capability.

## Linux evidence

Tested on Linux 6.8.0-1070-azure x86_64 in Codespaces. Real JSON snapshot showed available `/proc/stat`, CPU/I/O/memory PSI, meminfo, vmstat, cgroup v2 CPU, memory and I/O, and selected `loop0` diskstats. Two 100 ms JSON samples moved CPU and disk delta from `not_yet_sampled` to `available`; CSV sampling and the TASK 013 pressure snapshot also ran successfully. A missing explicit disk produced `unavailable`. Tests exercised a chmod-000 inaccessible file as the unprivileged Codespaces user, a missing file, a 257-entry temporary directory, freshness expiration, zero interval, counter reset and changed disk identity. GPU, thermal, power and physical hardware functionality: **NOT VERIFIED**; discovery access alone does not verify hardware functionality.

Focused tests and full workspace tests passed. `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo check --workspace`, release workspace and examples builds, and workspace documentation passed. One initial clippy run flagged a test permission literal; it was corrected and clippy passed afterward.

## Cost and limitations

Thirty separate release JSON snapshots with `--disk loop0`: median/max process wall latency 1.730/2.159 ms, internal sequential collection 0.587/0.707 ms, mean child CPU 1.620 ms per invocation. A separate 20-sample run at 100 ms intervals used 0.0174 CPU seconds over 1.923 wall seconds (0.90% of one core) and reached 2580 KiB peak RSS observed by 10 ms `/proc` polling. Measurements include serialization and process overhead as applicable, are environment-specific, and do not establish an optimization or system performance improvement.

TASK 015B can build a read-only IPC layer around this versioned representation, while preserving status, freshness, bounded output and process-local timestamp semantics. It must not assume host-wide visibility, atomic observations, physical hardware, or uninterrupted device identity. Validate deployment-specific freshness and resource budgets before using telemetry for control.
